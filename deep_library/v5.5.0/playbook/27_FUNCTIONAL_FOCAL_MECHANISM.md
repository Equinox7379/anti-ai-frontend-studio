# 功能性焦点机制

优秀产品界面的记忆点常常不是一款奇怪字体，而是用户第一次清楚看见了原本隐蔽的业务关系。

## 机制从关系中产生

| 信息关系 | 可成为焦点的机制 | 不合格替代 |
|---|---|---|
| 因果 | 输入—调整—派生—结果脊柱 | 六张 KPI 卡 |
| 证据 | 结论—规则—来源—复核追溯链 | 一个绿色“可信”徽章 |
| 比较 | 共享尺度、对齐差异和例外 | 三张独立方案卡 |
| 时间 | 事件、版本、影响和恢复点 | 装饰性时间线 |
| 网络 | 关系图与可达影响 | 只放节点气泡图 |
| 编辑 | 草稿、校验、提交与结果连续状态 | 分散的按钮和 Toast |
| 学习 | 判断过程、错误断点与补强动作 | 文章旁边放一道单选题 |

## 合格标准

功能性焦点必须写清：

```text
NAME：它叫什么
RELATION：它表达什么真实关系
TASK_EFFECT：它让用户更快或更可靠地做什么
RENDERED_FORM：它在桌面和移动端如何存在
INTERACTION：用户怎样进入、选择、展开或修正
REMOVAL_TEST：删除后哪项任务会具体变差
```

“独特标题字体”“大面积绿色”“动态图形背景”“一张漂亮插画”不能单独成为产品 UI 的功能性焦点。它们可以是表达材料，但必须依附于已经成立的产品机制。

## 熟悉框架＋专属机制

保留用户熟悉的导航、表单、表格、保存、错误和权限语法；把创新预算集中在核心关系上。这样既不会成为陌生的艺术实验，也不会回到通用后台模板。

## 移动端

桌面焦点机制不能只缩小。应保留相同关系，并重新排列：横向等式可以转成纵向推导；右侧证据栏可以转成行内展开或底部详情；比较矩阵可以优先显示差异列。移动端若丢失机制，说明它只是桌面装饰。

## 形式选择不能反过来吞掉关系

功能性焦点不等于“为每个节点做一个容器”。因果链优先连续表达，比较优先共享尺度，证据优先就地追溯。只有节点拥有独立状态或操作时才需要独立表面。删除边框和背景后，关系仍应成立。
